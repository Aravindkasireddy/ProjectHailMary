## CORE CLASSIFICATION PRINCIPLE

DevOps Engineer is the broad default for multi-domain automation roles spanning cloud infrastructure, Infrastructure as Code, CI/CD, deployment automation, observability, and operational delivery.

Choose a more specialized label when one domain clearly dominates the role responsibilities.

Do not promote a role into a specialist label from tool mentions alone. Specialist labels require evidence of ownership, architecture, lifecycle responsibility, standards-setting, or primary delivery scope in that domain.

---

## ROLE SIGNAL EVIDENCE MODEL

Use four signal layers for every active MAAS role. This is the current MAAS standard.

1. Core responsibility signals decide classification. They describe work the consultant must have performed, such as owning CI/CD release workflows, defining SLOs, triaging production incidents, operating Kubernetes clusters, building Terraform modules, automating Linux patching, or running data pipeline reliability.

2. Expanded workflow/tool signals strengthen a classification but cannot decide it alone. Tools such as Kubernetes, Terraform, Jenkins, Datadog, Spark, Airflow, Vault, or Azure DevOps are supporting evidence only when tied to ownership, troubleshooting, lifecycle, production, or automation responsibilities.

3. Implicit responsibility phrases count when the JD describes work without naming the exact tool. Examples:
- "reduce MTTR" → Site Reliability Engineer (SRE)
- "improve deployment safety" → DevOps Engineer or Continuous Integration (CI/CD)
- "self-service developer workflows" → Platform Engineering
- "standardize provisioning" → Cloud Automation Engineer
- "keep production environments stable" → DevOps Engineer, SRE, or Cloud Infrastructure Engineer depending on scope

4. Negative signals prevent keyword forcing. If the same tools appear inside product software development, customer enablement, generic support, retired cloud security/network/database specialist work, BI/reporting-only work, or monitoring-only escalation, do not force an active MAAS role.

Optional-only signals are non-blocking. Terms under nice-to-have, preferred, optional, bonus, plus, familiarity, or exposure sections may support rationale, but they must not trigger retired-role, niche-domain/product, software-development-dominant, generic-support, or role-alignment hard blocks unless the title or core required responsibilities make that risk central.

Classification should answer: "What prior-company use cases would the consultant need to explain in interview?" Prefer the role whose expected use cases best match the JD responsibilities.

Recent MAAS use-case anchors:
- SRE: incident response, SLO/SLI/SLA, observability setup, alert-noise reduction, Kubernetes reliability, RCA/postmortems, on-call, production performance tuning.
- DevOps: CI/CD pipelines, multi-environment deployment, Docker/Kubernetes deployment, release automation, rollback, secrets/certificates, deployment health monitoring.
- Cloud Automation: reusable Terraform/IaC modules, multi-account/environment provisioning, drift detection, Ansible/config automation, cost/DR automation.
- CI/CD: Jenkins/GitHub Actions/Azure DevOps ownership, build agents, artifacts, branch protection, rollback workflow, pipeline observability.
- Platform Engineering: Kubernetes platform support, GitOps, internal developer platform, reusable deployment templates, RBAC/secrets/policy, platform observability.
- Cloud Infrastructure: hybrid/cloud infrastructure, VM/server lifecycle, patching, backup/DR, infrastructure health monitoring, server/storage/network incident resolution.
- DevSecOps: security gates in CI/CD, secrets management, IAM/RBAC, image/dependency scanning, policy checks, compliance evidence automation.
- System Engineer: RHEL/Linux administration, Ansible/Bash/Python automation, systemctl/journalctl troubleshooting, patch management, AD/SSSD, storage/capacity, monitoring/logging.

Examples:

## EVIDENCE HIERARCHY

Weight evidence in this order:

0. Role nature (MANDATORY GATE — if customer-facing dominates, STOP before scoring)
1. Explicit ownership and scope
2. Repeated responsibilities
3. Required technologies tied to responsibility
4. Nice-to-have technologies
5. Job title

If the title suggests a specialization but the responsibilities do not support it, follow responsibilities and classify the actual work.

Do not classify from keyword stacking alone. For example:

* Kubernetes mention alone does NOT mean Platform Engineering
* Terraform mention alone does NOT mean Cloud Automation Engineer
* Prometheus/Grafana mention alone does NOT mean Site Reliability Engineer (SRE)
* IAM mention alone does NOT mean DevSecOps

Role-nature gate takes precedence over tool mentions.
If the role is primarily customer-facing technical enablement, treat it as OutOfScope even when DevOps/cloud tools are listed.

## TIE AND BORDERLINE RULES

When scores are close, apply these rules before final selection:

* If one role has stronger ownership evidence, choose that role even if scores are similar.
* If the top two roles are within 1 point and neither has strong ownership evidence, choose the broader label.

* Prefer OutOfScope over forcing an engineering label when the job is primarily business, analyst, support, or domain-application work.

## JD MAAS STANDARD SCORE

Set `jd_maas_standard.score` from 0 to 100 to answer one question only:

Does this JD itself meet MAAS standards for portable DevOps/SRE/cloud/platform/system/data-platform work?

This is not consultant fit and not model confidence.

Scoring guide:
- 25 points: active MAAS role family match.
- 30 points: portable responsibilities such as cloud infrastructure operations, IaC, CI/CD/release automation, Kubernetes/container operations, observability, incident response, Linux systems automation, or developer-platform enablement.
- 20 points: portable tools such as AWS, Azure, GCP, Terraform, CloudFormation, Kubernetes, Docker, Jenkins, GitHub Actions, GitLab CI, ArgoCD, Prometheus, Grafana, Datadog, Splunk, Linux, Ansible, Bash, or Python.
- 15 points: production/enterprise relevance such as production environments, SLO/SLA, on-call, incident response, regulated SaaS, multi-region, DR, or staging-to-production ownership.
- 10 points: JD specificity such as real responsibilities, required qualifications, experience requirement, and concrete tools.

Status:
- `pass` when score is 70 or above and no hard red flags exist.
- `review` when score is 50-69 and no hard red flags exist.
- `fail` when score is below 50 or any hard red flag exists.

Submission policy:
- Jobs scoring 50-59 are allowed to post into MAAS for staff review, but they are not consultant-submission or draft-generation eligible.
- Do not allow consultant profile submissions for jobs below 60% JD MAAS objective alignment.
- Scores 60-69 are submission-review-only; scores 70+ are the normal pass lane.
- Software engineer / software development jobs are not MAAS submission targets unless infrastructure, platform operations, Kubernetes/platform ownership, CI/CD/release engineering, observability, incident response, SRE, or cloud infrastructure operations are clearly the primary work.

Hard red flags always force `jd_maas_standard.status = "fail"` even if the score would otherwise be high.

## OUTPUT NORMALIZATION RULES

Before returning JSON:
- `strongest_label` must be one exact value from ROLE LABELS.
- `all_labels` must include `strongest_label` as the first item.
- `other_labels` must not repeat `strongest_label`.
- `all_labels` should usually stay at 1-3 labels.
- `apply_decision` must be exactly `APPLY` or `DO_NOT_APPLY`.
- `confidence_score` must be an integer from 0 to 100.
- `jd_maas_standard.score` must be an integer from 0 to 100.
- `jd_maas_standard.status` must be exactly `pass`, `review`, or `fail`.
- `dominant_domains` should list only the most relevant 1-3 scored domains.
- Every array in `dominant_signals` must exist, even when empty.
- `rationale_formatted` should use short fragments or bullets, not paragraphs.

For `cloud`:
- `is_cloud_role` = true only when cloud platforms materially appear in the delivery scope.
- `primary_cloud` must be `AWS`, `Azure`, `GCP`, or empty string.
- `cloud_providers` must contain only `AWS`, `Azure`, `GCP`.
- If more than one provider appears and no provider is clearly primary, leave `primary_cloud` empty and list all applicable providers.

For `decision_trace`:
- `top_score` is the highest domain score.
- `runner_up_score` is the second-highest domain score.
- `tie_break_applied` = true only when DOMAIN PRIORITY MODEL or a broad-vs-specialist judgment changes the selection.
- `priority_rule_used` should name the winning comparison when used, otherwise empty string.
- `strong_signal_override` = true only when ownership evidence overrode raw keyword closeness.

For `filters.domain_specialization`:
- Set it to `true` only when specialization is explicitly required or the work centers on domain systems rather than MAAS engineering scope.
- Do not set it to `true` merely because the company is in finance, healthcare, insurance, or telecom.

## CONFIDENCE SCORING GUIDE

Set `confidence_score` using this rubric:

* 90-100: dominant responsibilities, clear ownership, and clear technologies all align to one label
* 75-89: strong dominant pattern with minor overlap from adjacent domains
* 60-74: plausible best fit but responsibilities are mixed or partially ambiguous
* 40-59: weak evidence, thin description, or close competition between labels
* 0-39: highly ambiguous, contradictory, or mostly out of scope

Low confidence does not change the schema. It only lowers `confidence_score` and should be reflected in `rationale`.
