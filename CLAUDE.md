# Gemini-jobsearch — Project Reference

Multi-tenant job sourcing/matching platform for DevOps/SRE-type roles. Pipeline discovers jobs (Yahoo + ATS boards), filters/validates postings, classifies them with Gemini, upserts approved jobs to Supabase (the sole job-data store), and serves a Next.js dashboard.

## Stack
- **Backend**: Python 3.11+, stdlib `http.server` (no FastAPI/Flask), Playwright (WebKit) for scraping, BeautifulSoup, Apify (hosted scraping actors, see below), Supabase (Postgres+Auth+RLS), Gemini API for classification, OpenAI for resume tailoring, Discord/Slack webhooks.
- **Frontend**: `dashboard/` — Next.js 16.2.6 (App Router), React 19.2.4, Tailwind 4, TypeScript, Supabase JS client.
- **Infra**: Docker Compose (API on 8080, Web on 3000), GitHub Actions CI + auto-deploy to prod (see "Production deployment" below).

## Data flow
1. Dashboard triggers `POST /api/scrape` → spawns `find_and_scrape_jobs.py` → `scrape_and_filter_candidates.py` → `classify_and_save.py` (sequential subprocesses).
2. Classified jobs land in `approved_jobs.json` and get upserted to Supabase `public.jobs` (RLS-scoped by `user_id`).
3. Dashboard `GET /api/jobs` merges local JSON + Supabase rows, adds H1B sponsor matches and resume match scores.
4. After each pipeline run, newly approved jobs found in this run trigger an optional Discord/Slack webhook digest (or per-job alert) — no Notion sync; Supabase `public.jobs` is the sole job-data store.
5. Watched-company scheduler periodically subprocess-spawns `company_scraper/main.py` to upsert new jobs directly to Supabase.

Multi-tenancy: per-user scoping uses `MAAS_USER_ID`/`MAAS_USER_EMAIL` env vars and scoped filenames (e.g. `scraped_jobs_<email>.json`), plus Supabase RLS for the `jobs` and `user_configs` tables.

## Scraping methods by source
| Source | Method | Where |
|---|---|---|
| Greenhouse | Official JSON API (`boards-api.greenhouse.io/v1/boards/{slug}/jobs`) | `company_scraper/scrapers/greenhouse.py` |
| Lever | Official JSON API (`api.lever.co/v0/postings/{slug}?mode=json`) | `company_scraper/scrapers/lever.py` |
| Workday | **Apify-first** (`fantastic-jobs/workday-jobs-scraper` actor) → falls back to local Playwright Chromium if Apify unset/fails/empty | `company_scraper/scrapers/workday.py` |
| Generic / unknown ATS | **Apify-first** (`fantastic-jobs/jobs-scraper` actor, covers 12 ATS platforms) → falls back to local Playwright WebKit + BeautifulSoup | `company_scraper/scrapers/generic.py` |
| iCIMS | Local HTML scrape only (requests + BeautifulSoup, paginated `?iis=`) — **deliberately not on Apify**: `fantastic-jobs/jobs-scraper` does not support iCIMS (confirmed live — it logs "Skipping unsupported URL"); no dedicated iCIMS actor was found on Apify Store either | `company_scraper/scrapers/icims.py` |
| Yahoo job search (Stage 1 discovery) | Local HTML scrape of `search.yahoo.com/search?p=...` — no API, no Apify | `find_and_scrape_jobs.py`, `company_scraper/discovery.py` |

Apify integration: `company_scraper/scrapers/apify_client.py` wraps the `apify-client` SDK. Gated entirely by `APIFY_API_TOKEN` env var — if unset, Workday/generic scrapers behave exactly as before (local Playwright). Both Apify actors are from the same vendor (`fantastic-jobs`) and share an output shape (`title`/`description`/`locations`/`url`/`date_posted`), normalized via `_normalize_items()` in `apify_client.py` into this project's row shape (`job_url`/`job_title`/`company_name`/`job_description`/`location_work_type`/`requirement_id`). The `fantastic-jobs/jobs-scraper` actor's actual supported platforms are: Workday, Greenhouse, Ashby, Lever.co, BambooHR, JazzHR, Personio, Recruitee, Rippling, Rival, Teamtailor, JOIN.com — iCIMS is not among them, so don't re-attempt that migration without a different actor.

**Pre-check before calling the generic actor** (added 2026-06-22, real incident): confirmed live that calling `GENERIC_JOBS_ACTOR` against a host it doesn't support (e.g. Salesforce's custom careers site) logs "Skipping unsupported URL" and returns 0 items every time — 25 production Apify runs were burned this way in one day before the fix. `apify_client.generic_actor_likely_supports(url)` checks the URL's host against the actor's known-supported domain patterns (Ashby/BambooHR/JazzHR/Personio/Recruitee/Rippling/Teamtailor/JOIN.com/Workday/Greenhouse/Lever) before `generic.py` even attempts the call — unrecognized hosts skip straight to local Playwright, no wasted quota. Intentionally permissive on uncertainty: an unrecognized-but-actually-supported host costs one wasted call (same as before, not a regression), never blocks a genuinely supported one.

**Daily run cap**: `apify_client._check_and_increment_daily_usage()` caps Apify actor calls at `APIFY_MAX_RUNS_PER_DAY` (default 200/day, tracked in `logs/apify_usage.json`) to guard against runaway spend from the scheduler loop. Raising past the cap raises `RuntimeError`, which is caught by the same try/except that handles any other Apify failure — so hitting the cap just means scrapers silently fall back to local Playwright for the rest of the day, not a hard crash.

Test coverage: `tests/test_apify_scraping.py` covers `_normalize_items()` mapping, the daily cap, `run_actor` without a token, and that `generic.py`/`workday.py` fall back to local scraping when Apify raises.

## Module split (dashboard_server.py)
`dashboard_server.py` was a single ~4040-line file: ~50 module-level helper functions plus the `DashboardHandler` HTTP routing class. The pure/standalone helper groups (config persistence, stale-checking, Notion sync, H1B matching, watched-company scheduling, auth) were extracted into sibling modules — same function names/signatures/behavior, just relocated. **`DashboardHandler`'s do_GET/do_POST routing logic itself was deliberately left untouched** in that pass — moving ~40 route branches blind in the same change as the extraction was judged too risky. Where an extracted function needed state still owned by `dashboard_server.py` (`WORKSPACE_DIR`, `resolve_path`, `_invalidate_jobs_cache`, etc.), the new modules do a lazy `import dashboard_server as ds` inside the function body to avoid circular imports while always reading current values. Verified via `import dashboard_server` smoke test, full pytest suite, and a live server boot hitting `/api/health` + `/api/health/playwright`.

**Update**: the Notion sync module (`notion_sync.py`) and its SQLite mirror (`notion_sqlite_mirror.py`) described above were later deleted entirely when Notion support was removed (Supabase `public.jobs` is now the sole job-data store). The `users` table that briefly lived in a re-homed `user_auth_db.py` (`data/app_users.db`) was itself deleted shortly after — see "Auth" below, that whole local-login path was dead code.

**Worktree-merge gotcha**: the Notion-removal pass ran in an isolated worktree spawned from an earlier commit than `main` had advanced to (3 commits behind: the Apify-usage endpoint, the classifier rewrite, and critically the `JobCard.tsx` extraction). Merging main back into that worktree branch produced a real conflict in `page.tsx` (old inline per-job JSX vs. the new `<JobCard ... />` call) — resolved by keeping the componentized call but dropping the two Notion-sync props (`syncingJobUrl`/`onSyncJob`) it still referenced, then separately cleaning the equivalent dead "Sync Notion" button out of `JobCard.tsx` itself, which the worktree agent had never seen and so never touched. Lesson: when delegating a long-running worktree task, check `git merge-base` against current `main` before trusting a clean-looking diff — a stale branch point means components that didn't exist yet at spawn time won't get the same cleanup pass.

**Correction**: `tests/test_dashboard_auth.py` *does* exercise the route layer — it boots a real `ThreadingHTTPServer(DashboardHandler)` on a free port and hits real endpoints over HTTP (`/api/jobs`, `/api/scrape`, `/api/scrape/company`, `/api/scrape/status`, `/api/config`, `/api/policy`, `/api/analytics`, `/api/apify-usage`, health endpoints), asserting status codes and auth boundaries (401/403). It is not exhaustive — most of the ~40 routes still have no test — but the "zero route coverage" claim from the initial module-split pass was wrong; reuse this file's `test_server` fixture (module-scoped, spins up a live server) and `tests/conftest.py`'s `mock_auth` fixture rather than building new test infra when adding more route tests.

## Two POST routes were dead code (fixed 2026-06-30, found while adding route tests)
`/api/config/reset-target-titles` and `/api/classifier-feedback` always returned 404 regardless of auth, full stop — found while writing new auth-boundary tests for previously-untested routes (`tests/test_dashboard_auth.py`). Root cause in `dashboard_server.py`'s `do_POST()`: both were written as `elif` of the auth-gate `if parsed_url.path.startswith("/api/"):` a few lines above — that condition is always `True` for any `/api/` path, so the `elif` could never execute; the auth gate ran (hence the route "existing" enough to 401 without a token) but nothing ever wrote the actual response, falling through to a generic 404 once auth passed. Fixed by changing that first `elif` to a fresh `if`, making both reachable again; `/api/classifier-feedback` stays `elif` of *that* `if` (correct - mutually exclusive routes, both past the real auth gate). Tests: `tests/test_dashboard_auth.py` (route coverage expanded from ~9 to ~20 endpoints in the same pass; also corrected two route auth assumptions that turned out wrong on inspection — `/api/config/reset-target-titles` and `/api/watched-companies` (POST) are both in `_user_authed_post_paths`, any authenticated role, not admin-only).

## Auth
Login/signup is **Supabase Auth only** — `dashboard/src/app/page.tsx` calls `supabase.auth.signInWithPassword`/`signUp`/`onAuthStateChange` directly; there is no backend-issued session token. `DashboardHandler.get_auth_payload()` verifies the Bearer JWT via `supabase_client.verify_supabase_jwt()` on every `/api/*` request; `get_auth_role()` maps the Supabase `"authenticated"` role claim to `"admin"` only for the literal email `admin@hailmary.ai`, `"user"` otherwise (any other raw role value, e.g. a test-minted `"admin"`/`"user"`, passes through unchanged).

This used to have a *second*, parallel auth path: `/api/login`/`/api/register` backed by a local SQLite `users` table (`auth_helpers.py`, `user_auth_db.py`, `data/app_users.db`). Removed 2026-06-22 — confirmed via grep that the frontend never called those routes (it only ever used Supabase Auth), so the SQLite path was pure dead weight plus a real weak spot (hardcoded `admin123`/`user123` fallback passwords). Tests that used to call `/api/login`/`/api/register` to mint session tokens now use `tests/conftest.py`'s `mock_auth` fixture, which monkeypatches `supabase_client.verify_supabase_jwt` to accept arbitrary minted `(email, role)` tokens without touching real Supabase or a local DB — same testing capability, no backend dependency. Full suite is 33 tests post-removal (down from 35 — the two `/api/login`-specific success/failure tests no longer apply). Verified live on the VM: `/api/login` now 403 (falls through to the generic admin-required gate for unrecognized POST paths, since there's no more special-case for it — not a clean 404, but functionally gone either way), `/api/jobs` correctly 401 without a real Supabase JWT.

## Caching
There's an existing in-memory cache for `load_all_jobs()`: `_cached_jobs_data`/`_cached_jobs_mtimes` (dashboard_server.py, per-user-email keyed), invalidated via `_invalidate_jobs_cache(email)` whenever jobs are written. It's keyed on local JSON file mtimes, so it only helps the local-JSON merge path — there is no caching for Supabase queries, no HTTP-level caching (ETag/Cache-Control) on any `/api/*` response, and `get_h1b_sponsors_cleaned()` reloads/recomputes its sponsor list each call (own internal cache, separate from the jobs cache). Don't assume "no caching layer" when investigating perf — check `_cached_jobs_data` first.

## Duplicate jobs (fixed 2026-06-22)
Root cause was **not** in `near_dedup.py` — that module only *flags* near-duplicates (`is_duplicate`/`duplicate_of`/`duplicates` fields) by description-similarity, it never removes them, and **the frontend never read those fields**, so flagged duplicates still rendered. Fixed in `dashboard/src/app/page.tsx`: all job-category lists now derive from `dedupedJobs = jobs.filter(j => !j.is_duplicate)` instead of the raw `jobs` array.

The bigger source of duplicates was a separate bug in `find_and_scrape_jobs.py`'s LinkedIn-scrape path: `resolve_career_link()` → `resolve_career_link_with_llm()` asks Gemini/OpenAI to "find the most accurate direct URL" for a (company, title) pair with **zero grounding/verification** — LLMs reliably hallucinate plausible-looking but fake URLs (placeholder IDs like `?jobId=123456`, generic `/careers/index.jsp` listing pages). Every hallucinated/re-resolved URL became a *new* `job_url`, and since Supabase's uniqueness is `(user_id, job_url)`, each fake URL minted a brand-new duplicate row — confirmed at scale: KeyBank's "CI/CD Engineer" alone had 79 rows, one real company-wide audit found 619 of 3189 total `public.jobs` rows (≈19%) were duplicates across 310 `(company, title)` groups.

**Fix**: `scrape_linkedin()` now calls a new `_resolved_career_url_is_live()` helper before trusting a resolved URL — wraps `job_link_health.check_job_posting_live()` and only accepts the resolved URL if it's a genuine 2xx response (not stale, not uncertain/gated/error). Any ambiguity falls back to the real, stable LinkedIn URL instead of an unverified guess. Verified against real fabricated KeyBank URLs (correctly rejected) and known-live Workday/Greenhouse URLs (correctly accepted).

**One-time data cleanup** (2026-06-22): ran a one-off script (not committed — was a manual Supabase Python session) that grouped all `public.jobs` rows by `(user_id, normalized company_name, normalized job_title)` and deleted all but the most-recently-`scraped_at` row per group — 619 rows deleted, table went 3189 → 2570. Caveat: "most recent" doesn't guarantee "most correct" — some surviving rows are themselves generic careers-landing-page URLs rather than specific postings, since the cleanup didn't re-run liveness verification on survivors. If duplicates reappear for a given company, check whether the surviving `job_url` is actually a specific job page vs. a generic index page (the latter should probably be filtered at scrape time too — not yet done).

### Platform Engineering vs DevOps Engineer alignment (2026-06-27)
MAAS definition (user-specified): a **Platform Engineer is a DevOps specialist** whose primary scope is (1) deployments/containerization of applications, (2) Kubernetes lifecycle management (cluster creation, upgrades, autoscaling, node pools, multi-tenancy), (3) building/operating an Internal Developer Platform (IDP — Backstage, Morpheus, Harness IDP, or a custom portal), and (4) self-service developer workflows (golden paths, standardized templates, GitOps). **DevOps Engineer stays the broad default** for cross-functional CI/CD + IaC + deployment automation + observability ownership — Platform Engineering is only chosen when the Kubernetes-platform + IDP + self-service scope is clearly *dominant*, not merely present (e.g. a DevOps JD that mentions Kubernetes only as one tool among several stays DevOps Engineer).
- `Job_classifier_prompt.txt`'s `## PLATFORM ENGINEERING RULE` (the LLM-facing rule) was extended with this exact definition, named IDP products (Morpheus, Harness IDP, alongside the existing Backstage), an explicit "deployment and containerization ownership" core signal, and a worked-examples block showing which titles/JD shapes land in each label.
- `scripts/classify_and_save.py`'s `classify_job_dynamically()` (the zero-LLM rule-based fallback, used whenever Gemini *and* OpenAI both fail) got matching description-level keyword signals: named IDP products (`backstage`/`morpheus`/`harness idp`/`internal developer platform`, +3), self-service/golden-path language (+2), explicit cluster-lifecycle/node-pool/multi-tenancy language (+2), and a weaker bare-`kubernetes`-mention signal (+1) — weighted so a title with no "platform" in it can still correctly score into Platform Engineering when the JD body clearly describes that scope, while a DevOps JD with only incidental Kubernetes usage stays DevOps Engineer. Purely additive to one label's score; no other role's scoring changed. Tests: `tests/test_classify_rule_based.py` (3 new cases).

**Separate, real discovery-stage bug found and fixed in the same pass**: `find_and_scrape_jobs.py`'s `is_target_job()` — the Stage-1 discovery filter that gates which scraped jobs even get a `job_url` worth investigating further, used by both the main pipeline and `scripts/scrape_opt_sponsors_to_csv.py` — was silently rejecting the title `"Platform Engineer"` (and variants like `"DevOps Platform Engineer"`, `"Platform Reliability Engineer"`, `"Internal Developer Platform Engineer"`) against `config.json`'s target title `"Platform Engineering"`, because its substring/all-tokens check required the literal text `"engineering"` to appear in the job title, and `"engineering"` is not a substring of `"engineer"` (different suffix). Confirmed live via `git stash` round-trip: `is_target_job("Platform Engineer", [...])` returned `False` before the fix. Since this runs *before* the classifier ever sees the job, every "Platform Engineer"-titled posting was being dropped at discovery, not just misclassified. **Fix**: added `_stem_engineering()` — normalizes `"engineering"` → `"engineer"` on both the job title and each target title before comparison — applied to both the substring/all-tokens check and the Jaccard token-overlap fallback. Scoped to exactly one `config.json` entry (`"Platform Engineering"` is the only target title ending in `-ing`), so no other target title's matching behavior changed. Tests: `tests/test_is_target_job_platform_stemming.py` (6 cases: Platform Engineer variants now match, existing DevOps/SRE/CI-CD/etc. titles unaffected, unrelated titles still rejected).

**Where JD-content keyword filtering (Backstage/Morpheus/IDP/cluster-lifecycle signals) deliberately does NOT live**: not inside the ATS connectors (`company_scraper/scrapers/{greenhouse,lever,workday,generic,icims}.py`). Those connectors' job is to scrape and normalize raw postings (title + full `job_description` text) — full-JD-aware role judgment already correctly belongs to the classifier stage (`classify_job_dynamically()` / the Gemini/OpenAI prompt), which is where the new signals above were added. Duplicating JD-keyword scoring inside every connector would fragment a single judgment call across 5+ files for no benefit, since every connector already passes the full job description through unfiltered to the classifier.

## CI/CD gotcha: `secrets` context is not allowed in step `if:` conditionals
Hit this for real (2026-06-22): a `notify-on-failure` step had `if: ${{ secrets.DISCORD_BOT_TOKEN != '' && ... }}` — GitHub Actions rejects this as an **invalid workflow file** ("Unrecognized named-value: 'secrets'"), and when a workflow file is invalid, GitHub registers the run under the literal file path as its name with **zero jobs** and an immediate failure — not a job failure, the whole pipeline never starts. This broke `main` for one push (tests/build/deploy all silently didn't run) before being caught and fixed. The `secrets` context is only available in `env:`/`with:`/`run:` blocks, not `if:`. Fix pattern: move the secret into `env:`, then branch on it inside the `run:` shell script (`if [ -z "$SECRET" ]; then exit 0; fi`) instead of a YAML-level `if:`. If you ever add a new conditional step gated on a secret's presence, use this pattern, not `if: secrets.X != ''`.

## Scraping stress test findings (2026-06-23)
Real timing data from `logs/pipeline_metrics.jsonl` (46 runs) showed `find_and_scrape_jobs` (discovery) is the dominant bottleneck: median 428s but max 1653s — a 4x outlier. Root-caused two distinct issues, both fixed:
- **Yahoo search is persistently blocked from the VM's IP** (confirmed live: flat HTTP 500 on every request, not transient — 237 Yahoo errors / 119 circuit-breaker trips logged over a week). The per-title search ran in a `ThreadPoolExecutor(max_workers=2)`, and each worker independently discovered the same block via its own 5-consecutive-failure counter before the shared `SEARCH_STATE["aborted"]` flag could stop the others. Fixed with `_yahoo_reachable()` — one cheap probe before spinning up the worker pool; if Yahoo's down, skip the entire Yahoo-search phase (and the `expand_target_titles_with_gemini` synonym-expansion call) in one shot instead of N redundant rediscoveries. If Yahoo's block ever lifts, this self-heals automatically (probe succeeds, normal flow resumes) — no manual re-enable needed.
- **Single-Gemini-key rate limits skipped backoff entirely**: `classify_and_save.py`'s retry loop already had exponential backoff for transient errors, but the 429/quota branch tried `rotate_gemini_key()` first — which fails instantly with only one key configured (confirmed: production has exactly one `GEMINI_API_KEY`) — and then gave up immediately with zero retry, even though Gemini rate limits are often per-minute and would clear with a short wait. Fixed: a failed rotation now falls through to the same backoff-and-retry-same-key path (2s/4s/8s) instead of bailing immediately. Verified the fix actually changes behavior with a test that fails on the pre-fix code (`git stash` round-trip) and passes after.
- Playwright's `PLAYWRIGHT_LOCK` fix (see above) was stress-tested under real concurrency (not mocked) — 8 concurrent real browser sessions, 0 crashes, confirming the lock holds under genuine load, not just unit-test mocks.
- The real driver of pipeline behavior for a logged-in user is the Supabase `user_configs` row (`target_titles`, policy thresholds, etc.), **not** `config.json` — `config.json` is only the unauthenticated/default fallback. If a user reports "the feed feels off," check their `user_configs` row first, not just the repo's local JSON.
- `config.json`'s `target_companies` lists (Greenhouse/Lever/Ashby/SmartRecruiters slugs) drift dead over time as companies rename/retire their ATS boards — confirmed 16 dead 404 slugs on a 2026-06-22 live audit (pruned). Worth a periodic live-check sweep (hit each board's API directly) rather than assuming the list stays valid indefinitely. Don't run the check at high concurrency (20 workers) against companies with huge boards (some payloads are 40MB+) — caused false "dead" timeouts on re-check that were actually alive at lower concurrency/individually.
- **`find_and_scrape_jobs.py`'s `fetch_with_playwright()` is wrapped in `PLAYWRIGHT_LOCK`** (added 2026-06-22, real incident): the LinkedIn-scrape `ThreadPoolExecutor(max_workers=4)` calls it concurrently, but Playwright's *sync* API is not safe to drive from multiple threads at once — one thread's browser crash corrupts the shared driver state for every other concurrently-running thread, surfacing as `'PlaywrightContextManager' object has no attribute '_playwright'` cascading across all of them (observed live: a single crashed Chromium process degraded ~7 concurrent LinkedIn scrapes into slow/unreliable LLM-fallback parsing in the same run). Fixed by serializing all `sync_playwright()` usage behind one lock (`with PLAYWRIGHT_LOCK, sync_playwright() as p:` — single `with` statement, no re-indentation of the existing 100+ line body needed). This trades concurrency on the *browser session* for correctness; the threads still parallelize everything else (HTTP, parsing). If you add another concurrent Playwright call site, route it through the same lock rather than a new one.

## macOS-only fork-safety crash, separate from the earlier Playwright-thread-lock fix (fixed 2026-06-24)
The repeated "Python quit unexpectedly" crash dialogs on the user's Mac were **not** the same bug as the `PLAYWRIGHT_LOCK` thread-safety fix above, despite looking identical from the OS crash dialog alone. Pulled the actual `.ips` crash reports from `~/Library/Logs/DiagnosticReports/` (30 of them within a 5-minute window, all running off the last *committed* code, not any uncommitted work) and every single one had the identical faulting-thread backtrace: `fork() → _pthread_atfork_child_handlers → nw_settings_child_has_forked → nw_path_release_globals → NEFlowDirectorDestroy → _os_log_preferences_refresh → EXC_BAD_ACCESS`.

This is a documented macOS-specific issue: Apple's `Network.framework` fork-child cleanup handlers are not safe to run when CFNetwork/NSURLSession state exists from networking calls made on multiple threads (this script's `ThreadPoolExecutor` workers calling `requests.get()`) and something then calls `fork()` — which is exactly what `subprocess.Popen` does, including Playwright's own browser-launch path inside the already-`PLAYWRIGHT_LOCK`-protected `sync_playwright()` block. The lock prevents two `sync_playwright()` calls from racing each other, but does nothing to prevent *other* threads from making HTTP requests concurrently with a browser-launch fork — which is what actually crashes here. This never reproduces on the Linux production VM because `Network.framework` doesn't exist there; it's purely a local-dev-on-Mac issue.

**Fix**: at the very top of `find_and_scrape_jobs.py` (before any other imports), if running on macOS (`sys.platform == "darwin"`) as the main script and `OBJC_DISABLE_INITIALIZE_FORK_SAFETY` isn't already set, re-exec the interpreter (`os.execve`) with that env var set. This is the standard workaround for this class of crash, but it only works if set *before* the Objective-C runtime initializes — assigning `os.environ[...]` partway through the script is too late, hence the re-exec rather than a plain assignment.

**Real bug caught while writing this fix**: the first version gated only on `sys.platform == "darwin"`, with no `__name__ == "__main__"` check — which meant `import find_and_scrape_jobs` (e.g. from `tests/test_search_discovery.py`) triggered the re-exec too, silently breaking the entire pytest run (no output, exit code 2, no error message — pytest's own process was being re-exec'd mid-collection). Fixed by also requiring `__name__ == "__main__"`, so the workaround only fires on direct script execution (both local `python3 find_and_scrape_jobs.py` and `dashboard_server.py`'s `subprocess.Popen([sys.executable, "find_and_scrape_jobs.py"])` spawn path), never on import. Verified: `pytest tests/` passes (55/55) and `python3 find_and_scrape_jobs.py --help` runs without crash-looping.

## Career URL Cache — Optimization Sprint #1 (2026-06-27)
Real telemetry (see "Scraping stress test findings" decomposition work below) identified `career_url_resolution` as one of the largest `connector_extract` sub-operations (avg 1532ms/call), with zero caching — every LinkedIn job re-ran the full search/LLM resolution chain even when the same company had already been resolved minutes earlier (Top Companies telemetry showed heavy repetition: Netflix, Hyperproof, Tessera Labs, etc.).

**`career_url_cache.py`** (new module) caches `resolve_career_link()`'s Step 2 (search) / Step 3 (LLM) results, keyed **by normalized company name only** (via the existing `clean_company_name()` normalization, no new normalizer introduced) — a company's careers/ATS-board URL is invariant to job title, so a title-level secondary key would only fragment the cache for no measured benefit. Step 1 (direct ATS links scraped from that specific job's JD/HTML) bypasses the cache entirely — it's free/local and was never the slow part.
- **Storage**: a single JSON file (`logs/career_url_cache.json`), matching this repo's existing convention for small infrequently-written state (`config.json`, `policy_config.json`, `logs/apify_usage.json`) — no new infrastructure justified at current scale (a few hundred companies).
- **TTL**: configurable via `CAREER_URL_CACHE_TTL_SECONDS` env var, default 7 days — company ATS migrations are rare but config.json's target-company slugs are already known to go dead over weeks/months (see 2026-06-22 audit above), so a week bounds staleness without re-resolving every run.
- **Invalidation**: explicit (`career_url_cache.invalidate()`), automatic overwrite on every fresh resolution (`set_entry()`), and a debug bypass (`CAREER_URL_CACHE_DISABLE=1`). Wired into `scrape_linkedin()`'s existing live-URL-validation check — a cached/resolved URL that fails liveness now invalidates that company's cache entry (`failed_liveness_check` reason) instead of being served again until TTL expiry.
- **Behavior preservation**: on a cache miss or `CAREER_URL_CACHE_DISABLE=1`, `resolve_career_link()` falls through into the exact pre-cache Step 2/3 code, unmodified. Verified via `tests/test_career_url_cache.py` (19 tests: hit/miss/TTL/invalidation/overwrite/disabled/concurrency/telemetry/wiring).
- **Telemetry**: new `career_url_cache_lookup`/`career_url_cache_write`/`career_url_cache_invalidate` operation events (via the existing `_record_connector_substep`), and `scripts/analyze_pipeline_metrics.py`'s `career_url_cache_report()` reports hit/miss rate, avg lookup/write time, cache age, top cached/missed companies, and `estimated_yahoo_searches_avoided` (deterministic, not a guess — Yahoo is unconditionally the first call inside `search_for_job_url()`, so every avoided call is certain by construction). LLM-calls-avoided and DuckDuckGo-searches-avoided are deliberately *not* reported — both are reached only conditionally downstream, so the avoided count would be an unmeasurable counterfactual.
- **Benchmark** (`scripts/benchmark_career_url_cache.py`): splits the same `logs/pipeline_metrics.jsonl` at the cache's own first emitted event (a real, unambiguous boundary, not a guessed cutoff) into BEFORE/AFTER and compares real measured values. Live run captured a genuine **34.6% reduction in `career_url_resolution` avg (1524ms → 997ms)**, **48.7% P50 reduction (1565ms → 803ms)**, and **40.6% reduction in LinkedIn `connector_extract` avg (11006ms → 6538ms)** at a real **31.7% hit rate** (n=139 AFTER lookups, still growing) — re-run as more traffic accumulates before treating these as final.
- **Approval rate**: unaffected by construction, not just by assumption — `scripts/classify_and_save.py` only checks `job_url` for presence (`job["job_url"] and ...`), never uses it as classification input (title/description drive classification), and every cache hit returns the same class of URL the original search/LLM path would have found, subject to the same downstream liveness check either way.

## Classifier rule-based fallback bug (fixed 2026-06-23, real incident)
An external credibility audit of the live app found multiple "Data Scientist," "Engineering Program Manager," and "Sustainability Analyst" postings approved with `strongest_label="DevOps Engineer"` and `confidence_score=100`. Root cause in `scripts/classify_and_save.py`'s `classify_job_dynamically()` (the rule-based fallback used whenever Gemini *and* OpenAI classification both fail, which happens often given the single-Gemini-key rate-limit pattern above): when zero keyword signals matched any role family, the function defaulted `top_label = "DevOps Engineer"` with no red flag, so `apply_decision` fell through to `APPLY`. Zero signal should mean "don't know," not "default to the primary target label and auto-approve." Fixed: zero-signal jobs now get `strongest_label = "OutOfScope"`, a red flag (`"No rule-based keyword signal matched any MAAS role family"`), `apply_decision = DO_NOT_APPLY`, and a lower confidence score (30 instead of 85). Added `tests/test_classify_rule_based.py`, verified to fail on the pre-fix code via `git stash` round-trip.

**Separate, larger bug found and removed in the same pass**: `get_job_classifications()` was a ~540-line hardcoded lookup table of 40 specific job entries (`"Candidate 1: Actian - AI Engineer Intern"`, etc.), matched to *today's* real jobs purely by **array position** in `candidate_jobs.json`, not by content — `main()` built a `url_to_idx` map from the job's position in that file and looked up `classifications[idx]`. Since `candidate_jobs.json` is regenerated fresh every pipeline run with a different job set/order, today's job at slot N would silently inherit whatever unrelated historical job's hand-written classification and rationale text was hardcoded at that same slot. This was clearly a one-time manual-review batch that got permanently baked into the script instead of staying a one-off. Removed entirely (`get_job_classifications()`, the `url_to_idx`/`cls_idx` lookup in `main()`, and the now-dead `normalize_url()` helper + its now-unused `urlparse` import) — every job now goes through the real classifier chain (Gemini → OpenAI → rule-based fallback) unconditionally. `scripts/classify_and_save.py` went from ~1625 to ~1000 lines. Legitimate manual overrides have a proper path already: the dashboard's Inspect & Edit modal writes directly to Supabase (`apply_decision_payload`, `strongest_label`, etc.), not source code.

**One-time data cleanup from the same audit**: 34 already-approved Supabase rows still had `strongest_label` of `Cloud Security Engineer`/`Cloud Network Engineer` — both retired role families per the 2026-06-22 classifier rewrite, but approved *before* that rewrite and never retroactively reclassified. Bulk-updated via a one-off Supabase script (not committed) to `strongest_label = "OutOfScope"`, `apply_decision = "DO_NOT_APPLY"`, red flag `"Retired MAAS role family"`. The dashboard's role-filter dropdown (`dashboard/src/app/page.tsx`) is dynamically derived from `approvedJobs.map(j => j.strongest_label)`, not a hardcoded list — it was never out of sync with the *code*, it was reflecting genuinely stale *data*. If retired-role labels reappear in that dropdown, check for un-reclassified old rows, not a UI bug.

**UI credibility fixes from the same audit** (`dashboard/src/app/page.tsx`, `dashboard/components/JobCard.tsx`, `dashboard/src/app/layout.tsx`):
- Page `<title>` was the Next.js default ("Create Next App") — now "MAAS Sourcing Agent".
- Analytics "Approval Rate" rendered an unrounded float (e.g. `85.45612378...%`) — now `.toFixed(1)`.
- The three all-time stat cards (Approved/Unreviewed/Rejected counts) used the exact same label text as the separate "Last Run Results" bar above them, with no qualifier distinguishing cumulative inventory from one run's output — added explicit "(All-Time)" / "(This Run Only)" qualifiers to both.
- `JobCard.tsx`'s confidence score showed only a raw percentage (e.g. "100%"), which read as falsely authoritative on borderline matches — added a calibrated band label (Very Strong/Strong/Borderline/Review Needed) next to the existing percentage, not replacing it.

## Company scraper never classified jobs at all (fixed 2026-06-23, real incident)
While fixing the rule-based-classifier bug above, found a third, larger source of the same symptom: `company_scraper/publisher.py`'s `_row()` defaulted every job to `apply_decision="APPLY"`, `strongest_label="DevOps Engineer"`, `confidence_score=100` whenever those fields were missing — which was **always**, since `company_scraper/main.py` never ran any classifier before calling `upsert_jobs()`. `passes_it_job()` (the actual filter in that path) is a loose title/department IT-relevance heuristic, not the MAAS role classifier — it just decides "does this look IT-adjacent," then publisher.py auto-approved it as DevOps Engineer unconditionally. Confirmed live: "Perception Software Engineer - ADAS" and "Sr. Process Engineer, Body in White" (both automotive engineering, not DevOps) landed in the Approved feed this way, with `rationale="Company-targeted scrape"` as the only tell that no real classification happened.

**Fix**: `company_scraper/main.py` now runs every company-scraped job through `classify_job_dynamically()` (the same rule-based fallback the main pipeline uses, now fixed per above) right after the IT-relevance filter and before publishing — free, local, no extra Gemini/OpenAI cost. `publisher.py`'s own fallback defaults were hardened too, in case classification is ever skipped again: missing fields now default to `OutOfScope`/`DO_NOT_APPLY`/red flag `"Not classified"` instead of an unconditional auto-approve.

**Data cleanup**: 176 already-published rows had `rationale == "Company-targeted scrape"` (the literal tell that they were never classified). Re-ran all 176 through the fixed `classify_job_dynamically()` via a one-off Supabase script — **99 of 176 (56%) were wrongly auto-approved** and are now correctly `DO_NOT_APPLY`; only 77 were genuine DevOps-adjacent matches. This was the single largest source of false positives found across the whole audit. Tests: `tests/test_company_scraper_classification.py` (publisher.py defaults) and the added cases in `tests/test_classify_rule_based.py`.
